# 05 · 已知问题与注意事项（迁移前必读）

> 这份文档只写**实测发现的坑与诚实的边界**。目的是让接手的人少走我们走过的弯路，
> 并且**不要相信那些看起来能跑但其实会静默出错的路径**。

---

## 1. 平台与编码类（最容易一击致命）

### 1.1 ⚠️ Windows PowerShell 5.1 用 ANSI 代码页解码无 BOM 的 `.ps1`
**症状**：脚本里只要有中文，就会报 `Missing closing }` 之类的语法错误。
**规则**：**.ps1 必须纯 ASCII**；所有中文输出交给 Python 脚本。
现有的 `run-daily.ps1` / `publish-gh-pages.ps1` 都遵守这条，注释里也写了原因。

### 1.2 ⚠️ PowerShell 把原生命令的 stderr 当成终止错误
`$ErrorActionPreference='Stop'` 时，PS 5.1 会把原生程序写进 stderr 的**任何一行**变成
终止错误。`git` 连正常进度都写 stderr，Node 会写 `ExperimentalWarning`。
**症状**：Git 推送"失败"、agent 层报 `layer 2 threw, skipped` —— 而实际上都成功了。
**修法**：调用原生命令时临时降级为 `Continue`，并**只以退出码为准**。
现有代码在 `run-daily.ps1`（agent 调用）与 `publish-gh-pages.ps1`（`RunNative`/`Invoke-Git`）里都处理了。

### 1.3 ⚠️ 别用 PowerShell 的 `Set-Content` / `>` / `Tee-Object` 写中文 JSON/日志
会写 **BOM 或 UTF-16**，导致 JSON 解析失败、中文乱码。
**规则**：中文文件一律 Python 写（`ensure_ascii=False`）；
日志用 `[System.IO.File]::AppendAllText(..., UTF8Encoding($false))`。

### 1.4 ⚠️ 改时间/改字符串的批量脚本会误伤时间戳
真实事故：一个把 `14:00` 改成 `20:00` 的正则，**同时改掉了 ISO 时间戳里的时区偏移**
（`+08:00` → `+20:00`，202 处），还改坏了一个时间范围（`00:00-06:00` → `20:00-20:00`）。
**修法**：批量改写脚本必须带**安全检查**（改写前后对比非法偏移数量，异常就拒绝写入），
见 `scripts/set_schedule_hour.py` 的 `sanity_guard()`。

## 2. 前端与构建类

### 2.1 ⚠️ `app.js` 是**生成文件**，不要直接改
源文件是 `web/assets/js/*.part.js`，`node scripts/build.mjs` 把它们拼成一个
**classic script**（不是 ESM —— 为了 `file://` 也能打开）。
改了 `app.js` 下次构建就被覆盖。

### 2.2 ⚠️ 拼接后是**一个作用域**：重复的顶层 `const` 会让整页白屏
真实事故：新增 `const ACCENTS = {...}` 与主题调色板 `ACCENTS` 重名，
各自解析都正常，拼起来是 `SyntaxError`，**整页空白**。
`build.mjs` 现在会检查重复顶层声明并报出两个行号。

### 2.3 ⚠️ 视图是**一个大模板字符串**：一条数据异常会让整页失败
真实事故：`formulas.json` 里一条含 `\!` 的 LaTeX 让 `tex()` 抛异常，
「公式剖析」**整页**变成错误卡片。
**修法**：① 渲染器对畸形输入降级而不是抛（`renderGroup` 做了 null/类型强制）；
② 增加**门禁** `node scripts/check-formulas.mjs`，失败则拒绝发布。

### 2.4 布局溢出会被静默裁掉
这是本仓库出现过三次的同类问题（岗位面板错位、左栏状态条、顶栏按钮）。
**根因统一**：flex/grid 子项默认 `min-width: auto`（=内容宽度）无法收缩，
外层 `overflow: hidden` 把超出部分裁掉，**看起来像"缩窄"而不是溢出**。
**修法**：`app.css` 顶部有全局护栏（`* { min-width: 0 }`），
特例用 `flex: 0 0 auto` 反向选择；用 `node scripts/audit-layout.mjs` 测量而不是靠眼睛。

> **`audit-layout.mjs` 有已知误报**：`inline-flex` 元素的 `scrollWidth` 会虚报
> （例如统计条 `14/24` 被压扁）。工具已按严重度过滤，但**看到大量溢出时先核对截图**。

## 3. 数据与清理类

### 3.1 ⚠️ 清理工具**必须**写 blocklist，否则下一轮自动复活
真实事故：`prune_items.py` 下架了 165 条，但没有代码读它写的 blocklist，
下一轮采集**全部收回**（库从 554 反弹到 763）。
**修法**：采集器在**导入阶段**和**索引重建阶段**各检查一次。

### 3.2 ⚠️ `enrichment.json` 必须**合并**写入
整体覆盖会**不可逆地丢掉历史解析**。

### 3.3 反馈加分需要"重建"，否则删掉信号也不回落
加分烘进 `relevanceScore` 后，删 `feedback.json` 不会让它回落。
`collect.py` 每次启动会 `base = score - 旧bonus` 再按当前信号重算（幂等）。
实测删掉后 5 条残留加分被正确回退。

### 3.4 分类器的历史子串缺陷（已修，但值得记住）
修复前：`dit` 命中 `audit`、`intern` 命中 `international`、`ppo` 命中 `Opportunities`、
`基础` 命中比亚迪产业新闻。**修复后** ASCII 关键词按词边界匹配，CJK 仍用子串。
结论：**短英文关键词永远要按词边界匹配**，否则一定会污染分类。

### 3.5 零命中不等于 `trend`
修复前零命中默认归入 `trend`，导致语法学论文进趋势队列。
现在归 `unclassified` 并扣 12 分（可搜索但不占速览），且**不进深读队列**。

### 3.6 ⚠️ 硬件排除规则若整库匹配摘要，会误杀 CUDA / 锁 / C++ 文章
**症状**：`prune_items.py` 的「数字电路/硬件题」规则一旦对整个库跑
（`blob = 标题 + 摘要`），一批正常文章被判为硬件题：`自旋锁与互斥锁对比`、
`C++智能指针实现原理`、以及一篇 CUDA kernel 文章 —— 理由都是它们的摘要里出现了
**寄存器** / **状态转移**（内核实现确实会谈寄存器）。

**根因**：规则描述的对象是**题目**，代码却把它套在了**所有条目**上；而且硬件词在
真题目里出现在**标题**（`[编程题] 用3-8译码器实现全减器`），在普通文章里只出现在正文。

**修法**（`prune_items.py: noise_reason()`）：两个限定条件同时加 ——
① 只作用于**题目类条目**（`_is_question_item()`：有 `problemKind`，或渠道是
`nowcoder_questions`，或标题以 `[编程题]`/`[问答题]`/`[单选题]`/`[多选题]` 开头）；
② **只匹配标题**，不匹配摘要。规则 id 仍叫 `hardware-exercise`，但范围收窄到
「牛客那类真题」。

**推广**：凡是"排除某类主题"的规则，先问清楚它描述的是**条目**还是**页面上的某句话**。
写在摘要里的主题词是**内容**，写在标题里的才是**主题**。

### 3.7 ⚠️ 题库排序只按 `relevanceScore`，练手题会占满每日题解配额
**症状**：牛客题霸是**递进式**题单，开头是「判断字母」「及格分数」「计算一元二次方程」。
它们全都通过相关度门槛（题目确实含 `数组`/`字符串`/`输入` 等词），于是按
`relevanceScore` 排序时，每天 20 道题的**题解配额**被这些入门练手题吃掉，
读者拿不到「反转链表」「编辑距离」「栈的压入弹出序列」。

**根因**：`relevanceScore` 回答的是「这条内容是否切题」，**不是**「这道题值不值得写题解」。
而且题解配额是**稀缺资源**（默认 `--problems-max 20`），稀缺资源的分配顺序必须表达价值。

**修法**（`build_problem_bank.py`）：新增**实质度** `substance`（0–10）作为主排序键，
由三部分组成 —— 命中的算法主题权重（动态规划/图论/二叉树/链表 = 3.0，数组与矩阵 = 1.2）、
题面长度（200 字封顶加 3.0）、以及练手题惩罚（`TRIVIA_TITLE_RE` 命中 −3.0）。
`needsAnalysis` 仍排第一（先做没做过的），`relevanceScore` 只作最后的兜底排序。
规划器直接复用题库算好的 `substance`，不自己再算一遍 —— 否则两处对「值得写」的定义会漂移。

> 同一类错误的通用形态：**用"相关性"当"优先级"**。相关度是准入判断，
> 优先级要单独表达（这里用实质度，岗位库那里用梯队/`relevance` 公式）。

## 5. 定时任务的真实约束

| 事实 | 说明 |
|---|---|
| **不需要**任何 GUI 程序常驻 | 任务动作就是 `powershell.exe -Command "…run-daily.ps1"`，不需要 Harness 桌面程序 |
| **需要已登录 Windows** | 任务身份 `LogonType=Interactive`，登录界面下不会运行 |
| 错过会补跑一次 | `StartWhenAvailable=True`。当天开机且已登录后会补跑 |
| **不会唤醒休眠** | `WakeToRun=False`。休眠中不会跑 |
| 只有一个"每日"触发器 | 没有 logon/boot 触发器 → 重启本身**不会**触发运行 |
| 需要网络 | `RunOnlyIfNetworkAvailable=True`。发布还需要 `github.com` 可达 |

### 5.1 发布失败的语义（重要）
`github.com` 会抖动。**发布失败不影响本地数据**：
- 本地 `web/data/` 已更新
- 站点停在**上一次成功发布**的版本
- 日志里写 `publish FAILED`

**不要**因为发布失败就重跑整个流程 —— 只重跑发布即可。
脚本已有退避重试，但网络完全不通时重试也无效。

## 6. Agent 深读层的已知行为

### 6.1 任务量大时它会去做"基础设施"
实测：一次运行里 Agent 花了全部时间写 24 个批次的批处理脚本与校验器，
**没有产出任何深读内容**。
**对策**：用 `python scripts/scope_deep_read.py` 把队列缩到可完成规模；
或在提示词里明确"先产出 N 条，再考虑工具化"。

### 6.2 它可能只做一半就结束
实测：一次运行完成了 13 条新条目，但 `backfill` 的 45 条一条没动
（尽管提示词要求"两个清单都要处理"）。
**对策**：把 `queue` 清空、只留 `backfill`，它就会专心做 backfill。
**结论**：单轮工作量要收敛，不要指望一次做完 100+ 条。

### 6.3 弱模型的三类退化（迁移观察清单）
1. 图解质量下降（画极简方框，或用文字冒充图）
2. 纪律松动（编 URL、把推断写成结论、整体覆盖而非合并）
3. 产出规模失控（改去做工具化）

### 6.3b ⚠️ 它会顺手改**流水线脚本**，而 `git status` 不一定提醒你
**实测（2026-10-03）**：一次 layer 2 运行期间，`scripts/build_problem_bank.py` 被深读 agent
改写了（新增了 `curated` / `curatedAnalyzed` 的拆分，用于修「已解析的人工题 id 从题库里
消失，导致校验器把它们判成编造 id」）。**改动方向是对的**，但它是一次**无人 review 的
流水线改动**，而且当时该脚本还没被 `git add`，`git status` 只显示 `?? scripts/build_problem_bank.py`
（整体未跟踪），完全看不出「刚被改过」。

**判据与处置**：
```powershell
# 1) 找出 layer 2 运行窗口内被写过的脚本（按 mtime，比 git 可靠）
Get-ChildItem scripts -Recurse -File -Include *.py,*.mjs,*.ps1 |
  Where-Object { $_.LastWriteTime -gt (Get-Date).AddMinutes(-40) } | Sort-Object LastWriteTime
# 2) 逐个读关键函数，确认不是"看起来能跑但语义变了"
```
**预防**：新建脚本后**尽早 `git add`**（哪怕不提交），这样任何后续改动都会出现在
`git diff` 里；`daily-agent.md` 允许它写 `scripts/` 下的辅助脚本，但**不**授权它改
采集/规划/合并这类主流程脚本——发现被改就当代码评审对待，别默认它对。

### 6.4 ⚠️ 深读子进程消失会让整个流程静默挂住（实测，尚无超时保护）
**现象**：一次运行在 02:29:13 打出 `layer 2: agent deep read starting` 之后，
`harness-*.log` **13 分钟没有任何新增**，`run-daily.ps1` 进程仍存活（pid 20496），
但它的子进程（深读 agent）**已经不存在**——脚本在等待一个永远不会有输出的子进程。

**为什么会这样**：layer 2 走的是同步调用，且**没有超时**。子进程异常退出而父进程
没有捕获到退出、或输出管道保持打开时，`run-daily.ps1` 就会一直等下去。

**判断方法**（不要靠猜）：
```powershell
# 1) 日志最后一行的时间与当前时间差 —— 超过 10 分钟基本可判定为挂住
Get-Content web\data\logs\harness-<date>.log -Tail 5
# 2) 是否存在深读子进程（agent / dsh headless）
Get-CimInstance Win32_Process |
  Where-Object { $_.CommandLine -match 'run-daily|daily-agent|headless' } |
  Select-Object ProcessId, ParentProcessId, Name
# 父进程在、子进程不在 = 挂住，不是"还在算"
```

**处置**：layer 2 是**可选层**，语料与站点不依赖它。直接终止父进程，
然后用 `-SkipAgent` 把其余阶段跑完即可（实测 02:50 这样走完全流程并成功发布）：
```powershell
Stop-Process -Id <pid> -Force
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\run-daily.ps1 -SkipAgent -Force
```
**不要重跑整个流程** —— layer 1 已经完成，`manifest.lastRunAt` 与 index 都是自洽的，
重跑会浪费一次完整采集。先按上面第 1、2 步确认，再决定。

**待改进（诚实记录）**：`run-daily.ps1` 的 layer 2 调用应当加超时
（例如 `Start-Process` + `Wait-Process -Timeout`），超时后记 `WARN` 并继续后面的阶段，
而不是无限等待。目前**没有做这件事**，所以这个风险仍然存在。

## 7. 契约级"不要改"清单（迁移红线）

| 不要改 | 改了会怎样 |
|---|---|
| 稳定 id 算法（`sha1(sourceId+externalId)[:16]`） | 收藏/进度/解析全部失联，去重清零 |
| 时间戳必须带偏移 | 排序与新鲜度计算错乱 |
| `digest.items` 必须是索引的子集 | selfcheck 报 orphans |
| 分类 id 不可改名（只能新增） | 历史卡片分类失效 |
| `enrichment.json` 按 id 键控 + 合并写 | 丢历史解析 |
| `reviewPolicy` 的自动生效范围 | 放开后系统会自己改自己的评分标准 |
| 发布白名单 | 泄露 `state/` 与 `inbox/`（内部状态 + 个人备注） |

```bash

python scripts/audit_autonomy.py     # 期望 0 缺失
python scripts/audit_requirements.py # 期望 75/75
node scripts/check-parts.mjs
node scripts/build.mjs && node --check web/assets/js/app.js
node scripts/check-formulas.mjs      # 门禁
node scripts/verify-web.mjs          # 期望 15/15（无题解数据时 14/14）

```

**任何一项不达标都不要上线** —— 这些检查存在的唯一理由就是"曾经真的坏过"。
