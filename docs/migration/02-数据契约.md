# 02 · 数据契约（Data Contract）

> 迁移到任何平台时，**这份契约是唯一不能改的东西**。
> 接口 = `web/data/` 下的 JSON 文件；没有数据库、没有 HTTP API、没有 ORM。
> 下面每个结构都来自当前文件的实测。

---

## 0. 总原则

| 原则 | 说明 |
|---|---|
| **文件即接口** | 前端只通过 `fetch('data/*.json')` 读数据；没有服务端 |
| **`items/index.json` 是唯一真相** | 其它文件是它的视图、派生或侧车（sidecar） |
| **侧车与语料解耦** | `enrichment.json` / `formulas.json` 按 id 键控，重建语料不丢解析 |
| **id 必须稳定** | `sha1(sourceId + externalId)[:16]`，换平台**不要改算法** |
| **时间带偏移** | ISO-8601 + `+08:00`；内部算 UTC，展示 Asia/Shanghai |
| **原子写** | 一律 `写临时文件 → os.replace`，避免半截文件 |
| **UTF-8 无 BOM** | 中文 JSON 全部由 Python 写（`ensure_ascii=False`） |

### 稳定 id 算法（契约的一部分）
```python
def stable_id(source_id: str, external_id: str) -> str:
    return hashlib.sha1(f"{source_id}|{external_id}".encode("utf-8")).hexdigest()[:16]
```
**改了会怎样**：所有历史 `enrichment` / `formulas` / 收藏 / 学习进度**全部对不上**，
去重记忆清零。迁移时若必须改，要写一次性迁移脚本重映射 id。

## 1. `items/index.json` — 知识卡片全量（唯一真相）

```jsonc
{
  "generatedAt": "2026-10-02T02:04:49+08:00",
  "count": 550,
  "items": [
    {
      "id": "5edfee114f60afd1",          // 稳定 id，见上
      "sourceId": "github",               // 渠道 id（= CHANNEL_SPECS 的 key）
      "channel": "github",                // 通常与 sourceId 相同
      "externalId": "vllm-project/vllm",  // 渠道内唯一标识（决定 id）
      "category": "engineering",          // 必须是 taxonomy.json 里的 id，或 "unclassified"
      "title": "...",
      "summary": "...",                   // 采集摘要；可能来自页面 meta 回填
      "summarySource": "page-meta-description",  // 可选：说明摘要来源，可审计
      "url": "https://...",
      "canonicalUrl": "https://...",      // 去重用的规范 URL（可选）
      "sources": [{"url": "...", "name": "github"}],
      "authors": ["..."],
      "publishedAt": "2026-09-30T23:54:57+08:00",
      "fetchedAt": "2026-10-01T16:23:22+08:00",
      "lang": "en",
      "tags": ["inference", "cuda"],
      "relevanceScore": 95.0,             // 0–100
      "relevanceBreakdown": {             // 打分来源，便于审计
        "category": 32.0, "knowledge": 16.0, "freshness": 18.4, "quality": 8.0,
        "learningSignalBonus": 2.67       // 仅当有学习信号时出现
      },
      "categoryHits": ["inference", "serving"],   // 命中的关键词（空数组 = 未分类）
      // 知识类型：决定排序权重、深读优先级与卡片标签。九个取值：
      //   method 深度解析/论文 · interview 面经 · coding 算法题/手撕
      //   fundamentals 八股/基础 · job 岗位 · project 框架/实现
      //   news 资讯 · opinion 观点 · other 未归类
      // 判定顺序有讲究（见 collect.classify_knowledge_type 的注释）：
      //   1) 标题级明确标记（[编程题]/[单选题]/面经/题库汇总）优先
      //   2) 再看来源与 venue（arxiv/hf_papers/s2/peerReviewed → method）
      //   3) 代码仓库 → project（除非是通用工具）
      //   4) 最后才用标题+摘要的文本模式；且**非 method 的摘要级判定必须有标题独立支持**
      //      （否则「描述里含"数据结构与算法"」会把 LeetCode 题解仓库判成八股）
      "knowledgeType": "coding",
      "qualitySignals": {"stars": 93033, "forks": 22890, "codeAvailable": true},
      "peerReviewed": false,
      "codeAvailable": true,
      "stars": 93028,
      "firstSeen": "2026-10-01T16:23:22+08:00",
      "lastSeen": "2026-10-01T16:23:22+08:00",
      "contentHash": "61edca45c2ed42fb"   // sha1(title|summary)[:16]
    }
  ]
}
```

**派生字段（前端合并侧车后才存在，不在这个文件里）**：
`enriched` / `tldr` / `keyPoints` / `why` / `difficulty` / `concepts` / `selfCheck` /
`diagram` / `teaching` / `hasAnalysis` / `hasDiagram`。

> 前端在 `Store.boot()` 里把 `enrichment.byId[id]` 合并到对应 item 上再渲染。
> 这样「重建语料不丢解析、Agent 失败不污染语料」。

**`category` 的两个特殊值**：
- `unclassified` —— 没有任何关键词命中（会被扣 12 分，排在最后）
- 未知值 —— 前端 `mapCategoryAlias()` 会兜底映射，但**不要依赖兜底**，应写合法 id

## 4. `digest/today.json`（与 `digest/YYYY-MM-DD.json` 同内容）

```jsonc
{
  "date": "2026-10-02", "generatedAt": "...",
  "run": {"startedAt": "...", "finishedAt": "...", "status": "partial",
          "trigger": "scheduled",           // scheduled | manual | debug

  "items": [ /* 当天新增条目，含完整字段 */ ],
```

## 5. `enrichment.json` — 深读层产物（**与语料解耦**）

```jsonc
{
  "generatedAt": "...", "source": "daily-agent", "count": 45,
  "byId": {
    "<item id>": {
      "id": "<item id>",
      "tldr": "一句话结论，≤60 字",
      "keyPoints": ["3-5 条，每条 ≤40 字"],
      "why": "为什么对这个方向的求职者重要，≤80 字",
      "difficulty": "easy | medium | hard",
      "tags": ["英文小写标签"],
      "entities": ["方法名/机构名/模型名"],

      // ① 图解（硬性要求）
      "diagram": {
        "kind": "flow | architecture | curve | matrix | timeline",
        "title": "≤20 字", "caption": "一句话",
        "svg": "<svg viewBox='0 0 480 200' ...>...</svg>",  // 或
        "spec": {"type": "flow", "nodes": [{"label": "", "detail": ""}],
                 "edges": [{"from": 0, "to": 1, "label": ""}]},
        "alt": "读屏替代文字（必填）"
      },

      // ② 讲解层（用多种方式教同一件事）
      "teaching": {
        "progressive": [{"level": "一句话", "text": "..."},
                        {"level": "入门", "text": "..."},
                        {"level": "进阶", "text": "..."},
                        {"level": "专家", "text": "..."}],
        "socratic": [{"q": "追问", "a": "回答"}],
        "mechanism": "为什么必须这样设计（必填）",
        "boundary": "什么时候不适用 / 会失效（必填）",
        "analogyBoundary": "类比的失效点（必填）",
        "misconceptions": ["常见误解"],
        "ownAnalysis": "自己的思考；推断必须标注「（推断）」",
        "officialNotes": [{"position": "官方口径", "source": "数据里已有的 url 或来源名"}],
        "interviewAnswer": "可以照说的面试答法",
        "studyPath": {"prerequisites": ["..."], "nextSteps": ["..."]}
      },

      // ③ 概念易读化
      "concepts": [{
        "name": "...", "readable": "大白话 ≤100 字",
        "analogy": "具体的生活类比", "analogyBreaksDown": "类比在哪失效",
        "mechanism": "关键设计 + 解决了什么", "visual": "纯文本可视化方案",
        "prerequisites": ["..."], "selfTest": ["3 道自测题"], "formula": "LaTeX 或空串"
      }],

      // ④ 内联公式（同时也会被收进 formulas.json）

      "selfCheck": {
        "claims": ["能从摘要直接证实的断言"],
```

**合并规则（重要）**：写入时**必须读旧文件后合并**（新值覆盖同 id 的旧值），

## 6. `formulas.json` — 公式剖析（五层齐全）

```jsonc
{
  "generatedAt": "...", "source": "seed+daily", "count": 54,
  "formulas": [{
    "id": "f-attention",                       // 稳定 slug
    "name": "缩放点积注意力 (Scaled Dot-Product Attention)",
    "category": "multimodal|posttraining|worldmodel|generative|rl|agent|foundation|engineering",
    "glyph": "A", "tags": ["attention"],
    "latex": "\\mathrm{Attention}(Q,K,V)=...",  // 前端自研 tex() 渲染；必须能被它解析
    "symbols": [["Q ∈ R^{n×d_k}", "查询矩阵"]],  // 注意：数组的数组，不是对象
    "derivation": ["逐步推导，2-5 步"],
    "analogy": "生活类比",
    "code": "可运行的 PyTorch 片段",
    "pitfalls": ["面试易错点"],
    "sources": [{"title": "...", "url": "必须来自数据里已有的 url"}]
  }]
}
```

**五层必须齐全**：符号表 → 推导链条 → 生活类比 → 可运行代码 → 易错点。
缺层视为未完成（`audit_requirements.py` 会检查）。

> ⚠️ **LaTeX 必须能被自研渲染器解析**。它**不是**完整 TeX 实现。
> 一条解析失败的公式会让「公式剖析」**整页空白**（页面是一个大模板字符串）。
> 因此每日流程里有**门禁** `node scripts/check-formulas.mjs`，失败则拒绝发布。

## 7. `jobs.json` — 岗位 / 技能 / 题库

```jsonc
{
  "jobs": [{
    "id": "tencent-workbuddy-agent-harness",   // slug(company)-slug(title)
    "company": "...", "shortName": "...", "tier": "S|A|B|C",
    "title": "...",
    "directions": ["multimodal", "post-training", "world-model", "generative",
                   "rl", "agent", "infra", "embodied"],   // 只允许这些取值
    "cities": ["北京"], "pay": "...", "duration": "...", "conversion": "...",
    "open": true, "applyUrl": "...", "sources": [...],
    "relevance": 79                            // 由 build 时的公式计算，不要手改
  }],
  "skillMatrix": [{"id", "skill", "category", "importance", "demandCompanies",
                   "evidence", "howToProve", "learnCost", "sources"}],
  "handWrittenCoding": [{"id","title","difficulty","frequency","topics","prompt",
                         "keyPoints","pitfalls","referenceSolution","answerOutline",
                         "analysis"}],   // analysis 由每日题解挂载，见 §9.2
  "writtenExam": [ /* 同 handWrittenCoding 结构 */ ],
  "problemsAnalyzedAt": "2026-10-03T20:13:20+08:00",   // 题解最后一次挂载时间（可选）
  "interviewProcess": [{"company","stage","duration","format","typicalQuestions","tips","sources"}],
  "salaryBands": [{"company","role","daily","monthly","period","note","confidence","sources"}],
  "agentIncrements": [{"date","by","addedIds","at","note"}],   // Agent 增量记录
  "build": {"relevanceFormula": "...", "canonicalDirections": [...], ...}
}
```

**不变量**：`relevance` 由 `build.relevanceFormula` 决定，Agent 只追加条目、不改公式。
任何无法从原文确认的数字写 `null` 并在 `notes` 标「待核实」。

**人工题库的题解怎么挂进来**（`apply_enrichment.py: merge_curated_analysis()`）：
每日题解里 id 命中 `handWrittenCoding` / `writtenExam` 的那些，会把整个题解对象写到
**同一条目的 `analysis` 键**上（只加键、不覆盖人工字段），并更新顶层的 `problemsAnalyzedAt`。
**为什么加键而不是合并成一个扁平结构**：人工写的是 `prompt`/`keyPoints`/`pitfalls`/`referenceSolution`，
模型写的是 `restated`/`approach`/`complexity`/`code`/`diagram` —— 两者分开存，界面才能
「人工内容优先、模型内容补缺」，重跑题解也不会把人工结论改掉。

> 实测（2026-10-03）：11 篇题解全部是采集题（`pb-*`），所以**当前没有任何 jobs.json 条目带
> `analysis`**；键位是契约的一部分，但不要假设它一定存在。

## 9. `deep-read-plan.json` — 深读工作清单（Agent 的输入）

```jsonc
{
  "generatedAt": "...", "generatedBy": "plan_deep_read.py",
  "policy": {"perCategoryMin": 2, "perCategoryMax": 10, "freshOnly": false,
             "noiseRules": [{"id","why","patterns"}]},
  "totals": {"corpus": 550, "alreadyEnriched": 45, "candidates": 505,
             "skimmed": 115, "selected": 95, "categories": 12},
  "perCategory": {"multimodal": {"quota": 10, "picked": 10, "candidates": 52, "weight": 1.0}},
  "queue":    [{"id","title","category","channel","relevanceScore","depthScore",
                "url","hasSummary","scoreBreakdown"}],
  "backfill": [{"id","title","category","channel","url",
                "missing": ["diagram","formulas","teaching"], "backfillWeight": 6}],
  "backfillTotal": 45,
  "problems": [{"id","origin","kind","marker","title","topics","difficulty",
                "statement","sourceUrl","sourceName","itemId","channel","substance"}],
  "problemsTotal": 71,
  "problemsByOrigin": {"collected": 20, "curated": 0},
  "skimmed": [{"id","title","category","rule","why"}],   // 被闸门挡掉的（可审计）
  "skimByRule": {"referral-code": 3, "category-mismatch": 112}
}
```

- `queue` = **尚未深读**的条目
- `backfill` = **已深读但解析不完整**的条目（按 `missing` 补，不要重写）
- `problems` = **题解队列**（题库定位）。`origin: "collected"` 来自题库清单，
  `origin: "curated"` 来自人工题库；`substance` 直接抄自题库，保证规划器与题库对
  「哪道题更值得写」的判断一致。
- 排进 `problems` 的条目会以 `rule: "problem-queue"` 出现在 `skimmed`/`skimByRule` 里 ——
  它**不是被丢弃**，而是改用题解的形式解析（见 01 §3.3）。

## 9.1 `problem-bank.json` — 题库清单（确定性，题目→题解的输入）

```jsonc
{
  "generatedAt": "...", "source": "build_problem_bank.py",
  "corpusSize": 734,                    // 生成时的语料量，用于识别旧快照
  "stats": {"total": 35, "hand": 26, "exam": 9,
            "analyzed": 11, "pending": 24, "curatedPending": 47},
  "problems": [{
    "id": "pb-<itemId>",                // 契约：采集题固定前缀 pb- + 卡片 id
    "itemId": "0e03dc46f5fbdb16",       // 对应 items/index.json 的 id（采集题才有）
    "kind": "hand | exam",              // 手撕代码 / 笔试客观题
    "marker": "编程题",                  // 原始标记（[编程题]/[问答题]/…），清洗后的标题不含它
    "title": "两数之和",                 // 已去掉站点后缀与 [标记]
    "statement": "题面（来自条目 summary，原样，不改写）",
    "topics": ["链表", "动态规划"],       // 最多 6 个，来自 TOPIC_RULES 词典
    "difficulty": "easy|medium|hard",   // 源站给了就用源站的，否则 estimate_difficulty()
    "substance": 6.4,                   // 0–10，决定题解配额优先级（见下）
    "sourceUrl": "https://...", "sourceName": "牛客题库",
    "channel": "nowcoder_questions",
    "relevanceScore": 63.2,             // 抄自卡片，仅供展示/兜底排序
    "codeAvailable": false,
    "needsAnalysis": true               // false = problem-analysis.json 里已有题解
  }],
  "curated": [{
    "id": "batchnorm", "kind": "hand", "marker": "手撕代码",
    "title": "手写 BatchNorm2d（训练/推理行为差异）",
    "statement": "人工写的题面/提示", "topics": ["normalization", "cv"], "difficulty": "medium",
    "sourceName": "人工整理（research/jobs_kb.json）", "origin": "curated",
    "has": {"keyPoints": true, "pitfalls": true, "solution": true, "answerOutline": false},
    "needsAnalysis": true
  }]
}
```

**谁写谁读**：`scripts/build_problem_bank.py` 写（读 `items/index.json` + `jobs.json`；
`problem-analysis.json` 只用来算 `needsAnalysis`）；`plan_deep_read.py` 读它生成 `problems` 队列；
前端 `core.part.js` 读它渲染「算法题库」分段；`selfcheck.py` 与 `audit_requirements.py` 断言它。

**`problems` 与 `curated` 为什么分开**：`curated` 里的题**已经**由 `jobs.json` 渲染成卡片
（`build_problem_bank.py` 是从 `jobs_kb.json` 复制过来的），如果把它们再塞进 `problems`，
同一个问题会在前端出现两次。分开存还能表达一个区别：采集题只有题面，人工题**已经有人写了**
`keyPoints`/`pitfalls`/`answerOutline`，所以 `has` 字段告诉 Agent「哪几层不用重写」。

**id 规则**：采集题 `pb-<itemId>`（卡片 id 是 `sha1(sourceId+externalId)[:16]`，见 §0）；
人工题沿用人工 id（如 `hand-lru-cache`）。**两套 id 不可互换**，`problem-analysis.json` 的键
就是这里的 id，所以题库重建不会让已有题解失联（条目 id 稳定 → `pb-` id 稳定）。

**排除规则（三道，全在 `build_problem_bank.py` + `collect.py`）**：

| 规则 | 依据 | 为什么 |
|---|---|---|
| 不是题目 | `problem_meta()` 只在三种情况下认定：渠道是 `nowcoder_questions`（或 URL 含 `/questionTerminal/`）→ 手撕/客观题；渠道是 `programmercarl` 且 URL 含 `/algo/` 或 `/hot100/` → 手撕题 | 一个仓库可以有 500 个解法，但它不是一道"能被问的问题"；标记成题目会让「待解析」失去意义 |
| 硬件/数字电路 | `PROBLEM_EXCLUDE_RE`（编码器/译码器/触发器/FPGA/verilog…） | 牛客题霸按分类排序，抽一片就可能是 11 道 FPGA 题；对算法岗求职无价值 |
| 不是题面 | 手撕题必须命中 `TASK_STATEMENT_RE`（输入/输出/给定/实现/样例…），摘要 <40 字直接丢 | 「字符串学习路线」这类索引页是正当的卡片，但给它写题解没有意义 |

> ⚠️ 这三道都是**关键词规则**，会漏。实测 2026-10-03：`pb-0e03dc46f5fbdb16`（「字符串学习路线」）
> 因为摘要里出现「判断」二字通过了 `TASK_STATEMENT_RE`，仍在题库里。**任何"题库里出现路线页/仓库页"
> 的观察都以这份文件为准，不要相信注释里"已排除"的说法。**

**`substance`（实质度，0–10）为什么存在**：牛客题霸是**递进式**题单，开头是
「判断字母」「及格分数」「计算一元二次方程」这类练手题 —— 它们是真题，也确实该进题库，
但如果按 `relevanceScore` 排序，这些题会占满每天 20 道题的题解配额，读者拿到 20 篇
「如何判断奇偶」而不是「反转链表」「编辑距离」。所以排序信号必须是内容实质度：

```
substance = Σ TOPIC_WEIGHT[命中的算法主题]        // 动态规划/图论/二叉树/链表 = 3.0，数组与矩阵 = 1.2
          + min(3.0, len(statement)/200)          // 60 字的题面撑不起一篇题解
          - 3.0 (若标题命中 TRIVIA_TITLE_RE)      // 判断字母/及格分数/温度转换/打印图形…
          → 截断到 [0, 10]
```

`difficulty` 同样是**估计值**（源站很少公布）：硬主题命中 ≥2 个或题面 >500 字 → `hard`；
练手题或（无主题且题面 <150 字）→ `easy`；其余 `medium`。

## 9.2 `problem-analysis.json` — 逐题题解（深读层产物）

```jsonc
{
  "generatedAt": "...", "source": "seed+daily-agent", "count": 11,
  "byId": {
    "pb-0fe3d8b02701d756": {
      "id": "pb-0fe3d8b02701d756",      // 必须与题库清单的 id 完全一致
      "itemId": "0fe3d8b02701d756",     // 采集题才有；人工题没有这个键
      "tldr": "一句话结论 ≤60 字",
      "restated": "题意澄清（输入/输出/约束/样例；题面被截断就写明截断在哪）",
      "approach": [{"step": "暴力", "detail": "..."}, {"step": "最优", "detail": "..."}],
      "complexity": {"time": "O(n)", "space": "O(1)", "why": "代价来自哪里"},
      "code": {"language": "python", "source": "完整可运行的实现（≥120 字符、≥4 行）",
               "walkthrough": [{"note": "逐块说明"}]},
      "edgeCases": ["空输入", "n=1"],
      "pitfalls": ["面试最容易写错的地方"],          // 必填非空
      "followUps": ["面试官追问"], "variations": ["同源变形题"],
      "diagram": {"kind": "flow", "title": "≤20 字", "caption": "...",
                  "svg": "<svg viewBox='0 0 480 240' ...>", "alt": "..."},
      "selfTest": ["自测题"], "keyPoints": ["得分要点"],
      "sources": [{"title": "题目出处", "url": "只能是题目自身的 sourceUrl 或题面里的链接"}],
      "selfCheck": {"claims": [...], "uncertain": ["题面截断/样例缺失等"]}
    }
  }
}
```

**与 `enrichment.json` 的关系（重要）**：题解**不是**卡片，两者形状不同 ——
卡片有 `concepts`/`formulas`/`teaching`，题解有 `restated`/`approach`/`code`/`diagram`。
所以题解存独立文件（`enrichment.json` 已是 MB 级，浏览器每次加载都要抓，不该为了题库定位背代码块），
但**采集题会被投影成一张轻量卡片**（`apply_enrichment.py: problem_analysis_as_enrichment()`），
让卡片库也显示「已深读」与同一张图解，而不是看起来没解析过：

- 投影卡片带 `derivedFrom: "problem-analysis.json"` 与 `problemAnalysisId`，`concepts`/`formulas` 为空；
- **不覆盖富卡片**：若该 id 已有带 `concepts` 的卡片，直接跳过（`never downgrade a richer existing card`）；
- 所以 `enrichment.json` 的 `count` 会**大于**卡片语料里"被人工/深读写过"的条目数，这是正常的。

**合并语义「只增不减」**：`merge_problem_analysis()` 先读旧文件再按 id 覆盖同 id 条目，
**不在本轮 payload 里的旧题解一律保留**。原因：题解是逐日累积的资产，某天 Agent 只做了 3 道题，
不应该把上周的 50 篇题解删掉。`count` 字段恒等于 `byId` 的长度（`selfcheck.py` 会断言一致）。

**校验（发布前）**：`validate_problem_analysis.py` 是唯一的题解校验器（卡片校验器
`validate_agent_out.py` 的形状规则会拒绝所有正确题解）：

| 检查 | 规则 | 为什么 |
|---|---|---|
| 代码是真的 | `code.source` ≥120 字符、≥4 行非空、非 `pass`/`...`/`# TODO`、含 `def/for/while/return` 等结构 | 读者的原始抱怨就是「只给仓库链接」；`def solve(): pass` 是同一个问题的精致版本 |
| 图解自包含 | 与卡片同一套 SVG 规则（`viewBox`、无 `<image>`/`<script>`、字号 ≥13、只用主题色） | 图解要在 6 套主题下离线渲染 |
| 不编造 URL | `sources[].url` 只能是该题的 `sourceUrl` 或题面文本里已出现的链接 | 题解是模型写的，链接是最容易被编出来的字段 |
| 不确定要标注 | `selfCheck.claims` / `uncertain` 必须存在（可为空数组） | 题面被截断时，「样例待补」必须写出来而不是脑补 |

```bash
python scripts/validate_problem_analysis.py --date 2026-10-03 --strict   # 校验批次
python scripts/validate_problem_analysis.py --only pb-abc123,pb-def456   # 只校验指定题（并行写批次时用）
python scripts/validate_problem_analysis.py --merged                     # 校验合并后的 web/data/problem-analysis.json
```

## 16. `interview.json` — 面经结构化抽取（可选，每日生成）

```jsonc
{
  "generatedAt": "...", "source": "build_interview_index.py (deterministic rules, no LLM)",
  "count": 26,
  "companies": [{"name": "字节跳动", "count": 5}],
  "rounds":    [{"name": "一面", "count": 14}],
  "topics":    [{"name": "项目/论文深挖", "count": 15}],
  "outcomes":  [{"name": "通过", "count": 18}],
  "withCoding": 5,
  "items": [{
    "id": "...", "title": "...", "url": "...", "channel": "nowcoder",
    "publishedAt": "2026-10-01T...", "company": "字节跳动", "round": "二面",
    "outcome": "未通过", "topics": ["工程/系统"], "hasCoding": true
  }]
}
```

**为什么要单独一层**：面经条目的 `summary` 是论坛原帖（吐槽 + 流水账 + 内推码），
而面经又是**时效性最强**的内容 —— 想回答"字节二面考了什么"不该让你逐条点开。
这一层把公司/轮次/结果/主题抽成结构化字段，直接支撑「面经速览」面板。

**为什么用规则而不是模型**：规则会漏，但**不会编**。面经标题写法高度固定，
规则足够准且每一条都能对着原帖核对；模型抽取放在深读层做补充。

两个实测踩过的抽取坑（都写在代码注释里）：
1. **结果判定必须先测负面**。`凉经`（失败）曾被判成"通过"，因为宽松的 `offer`/"过"
   先命中了；现在顺序是 未通过 → 待定 → 通过。
2. **不能只靠标题里有"面试"**。宽松匹配会把"千万不要对面试官抱有太多滤镜！"
   "offer选择求助"这类**没有面试内容**的帖子算进来；现在要求标题含
   面经/挂经/凉经/笔经，或含明确的轮次词（一面/二面/三面/HR面）。

## 17. 契约违反的后果（迁移时最容易忽略）

| 违反 | 后果 |
|---|---|
| 改了 id 算法 | 收藏、进度、解析全部失联；去重失效 |
| `category` 用了 taxonomy 里没有的值 | selfcheck 警告；UI 走兜底映射 |
| `digest.items` 不是 index 的子集 | selfcheck 报「orphans」 |
| 时间戳不带偏移 | 排序/新鲜度计算错乱 |
| 写 JSON 用了 BOM | JSON 解析失败，页面空白 |
| 整体覆盖 `enrichment.json` 而非合并 | **丢失历史解析**（不可逆） |
| 整体覆盖 `problem-analysis.json` 而非按 id 合并 | **丢失历史题解**（题解是逐日累积的资产） |
| 题解 id 与题库清单不一致（改 `pb-` 前缀或人工 id） | 题解成为孤儿：前端永远不显示，`selfcheck` 报孤儿警告 |
| 让题解投影卡片覆盖已有富卡片 | 卡片库的 `concepts`/`formulas` 被清空（代码里已按「不降级」跳过） |
| 把 `state/` 或 `inbox/` 发布到公网 | 泄露内部状态与个人备注 |
| `formulas[].latex` 用了自研渲染器不支持的命令 | **公式页整页空白**（有门禁拦） |
